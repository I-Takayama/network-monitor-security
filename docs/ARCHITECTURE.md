# システム構成・技術選定記録

## 1. 解決したい問題

単発のTCP接続結果のみでは、次の区別が難しい。

1. 接続できない一時的な通信障害
2. 接続できても期待するHTTP応答を返さないアプリケーション障害
3. 認証失敗が短時間に集中するセキュリティ上の兆候
4. 監視ログ自体が更新されず、現在の状態を判断できない状況

本開発では、異なる層の観測情報を分離し、理由の分かる判定と履歴を提示することを目指した。

## 2. 実証環境と公開範囲

開発・実証環境：

```text
Windows
 ├─ PowerShell / タスクスケジューラ
 │    └─ SSH鍵 + SCPによる認証ログ取得
 ├─ WSL Debian
 │    ├─ C言語監視本体
 │    ├─ TCP/HTTP異常検知
 │    ├─ 認証TSV集計
 │    └─ Web API / Dashboard
 └─ VMware上のUbuntu Server
      ├─ FastAPIによる模擬金融API
      ├─ GET /health
      ├─ POST /login
      ├─ GET /balance
      └─ 認証イベントJSONL
```

WSLからUbuntuへはSSHトンネルを使い、HTTPサービスを外部に直接公開せず監視した。

**公開候補に含むもの**：C監視本体、Web画面、C検知器、テスト、設定例、説明資料。

**現時点で含まないもの**：FastAPIアプリ本体、Windowsの定期収集スクリプト、秘密鍵、認証生ログ、正規化TSV、実機固有の設定。

## 3. 主な技術の説明と選定理由

| 技術 | どのようなものか | 採用した理由 |
|---|---|---|
| C言語 | OSのソケットAPIを直接利用できる言語 | 通信・エラー処理・メモリ・状態管理を理解するため |
| TCPソケット | IPアドレスとポートに対する通信経路 | ポートの接続可否を実測するため |
| pthread | POSIXのスレッドAPI | ポートごとに並列監視するため |
| mutex | 共有データへの同時アクセスを制御する仕組み | Web表示用の監視結果を競合から保護するため |
| HTTP GET | URLのリソース取得を要求するHTTPメソッド | TCP接続成立だけでなくアプリケーションの応答を見るため |
| CSV | カンマ区切りの表形式テキスト | 時系列履歴を簡単に保存・比較できるため |
| JSON | 名前付きの値を表現できるデータ形式 | ブラウザから監視状態を取得しやすいため |
| FastAPI | PythonのWeb APIフレームワーク | 模擬金融APIと認証挙動を少ない実装量で用意するため |
| Ubuntu Server | サーバ向けLinuxディストリビューション | SSH、ファイアウォール、サービス運用を実機に近い構成で学ぶため |
| WSL Debian | Windows上でLinuxを実行する環境 | 普段のWindows環境からLinux向けCコードを開発するため |
| SSHトンネル | SSH接続を介して通信を転送する仕組み | APIを外部公開せず検証ネットワークから利用するため |
| SHA-256 | データの同一性確認に使うハッシュ関数 | 既存ログが途中で書き換わっていないかを確認するため |

## 4. 代替案と判断

- **Pythonで全監視機能を作る案**：開発効率は高いが、今回はCのソケット・並列処理・エラー処理を理解する目的を優先。模擬APIはPythonに分担した。
- **TCP接続可否だけを見る案**：HTTP 500など、接続できるがアプリケーションに問題がある状態を捉えられない。HTTP応答の期待値判定を追加した。
- **認証失敗件数の累計だけを見る案**：時間的な集中を表せない。60秒の移動窓で同じ送信元IP・ユーザー名別に5回の失敗を判定した。
- **認証イベント時刻だけで収集鮮度を判断する案**：ログインが発生しない正常な時間帯も収集停止と誤認する。別のheartbeatを設け、収集成功時刻を判断する方式に分離した。
- **監視データを1つの巨大JSONにまとめる案**：既存APIの互換性に影響する。TCP/HTTP用の `/api/status` と認証用の `/api/auth-status` を分離した。

## 5. 主要モジュール

- `src/main.c`：設定読込、ポート別監視、スレッド管理
- `src/scanner.c`：TCP接続と接続結果の取得
- `src/anomaly.c` / `src/health.c`：TCPの異常イベントと期待状態に対する判定
- `src/http_probe.c`：HTTP GETと応答取得
- `src/http_health.c` / `src/http_anomaly.c`：HTTP応答の期待値・継続異常・復旧判定
- `src/auth_anomaly.c`：60秒窓での認証失敗集中の検知
- `src/auth_status.c`：認証TSVの履歴再生と収集鮮度評価
- `src/webserver.c`：ローカルWeb APIとHTML配信
- `src/logger.c`：監視結果をCSVへ記録

## 6. 判定とその意味

### TCP

主な観点は、前回からの状態変化、1000ms超の応答遅延、3回以上の連続失敗。これらの異常イベントと、期待状態に対するHealth判定は別の概念として扱う。

### HTTP

期待するステータスコードとの不一致、通信上のエラー、1000ms超の遅延、3回以上の連続異常、および回復を区別する。HTTP Healthが期待ステータスと一致していても、応答遅延による異常イベントは発生し得る。

### 認証

60秒以内の失敗5回を送信元IP・ユーザー名別に判定する。集計用Web APIには個別の送信元IP・ユーザー名を含めない。元データの認証TSVには識別情報が存在し得るため、別途保護が必要。

### ログ鮮度

認証スナップショットと収集成功heartbeatを確認し、原則120秒以内の更新をfreshとして扱う。収集できない状態を単純な「警告0件」とはみなさない。

## 7. 研究との関係と未達成事項

現在できていることは、多層の監視データを取得・表示し、個別の異常を理由付きで判定すること。

まだ実証していないことは、実際のサイバー攻撃と内部障害を高精度に識別できるという主張、Precision/Recall/FPRに基づく比較評価、商用環境への適用効果である。

卒業研究では、それらを別途、実験条件と評価指標を定義して検証する。
