# Network Monitor

**TCP接続、HTTP応答、認証失敗の集中を確認するC言語製の監視ツール**

Network Monitorは、ネットワークの接続状態とWeb APIの応答を定期的に記録し、設定した条件から外れた状態を検知する個人開発ツールです。模擬金融APIを対象に、認証失敗の集中とログ収集の停止も確認できるように拡張しました。

このリポジトリは**公開準備中のC言語監視本体**です。実験で使用したFastAPIの模擬金融APIとWindowsの認証ログ自動収集スクリプトは、現時点では含めていません。

## 開発の目的

開発当初は、指定したIPアドレスとポートにTCP接続できるかを調べる機能から始めました。しかし、接続に成功しただけでは、アプリケーションが要求どおりに応答しているとは限りません。また、接続失敗が一度発生した場合と、繰り返し発生している場合では、状況の捉え方が異なります。

そこで、次の情報を分けて記録・判定する設計にしました。

- **TCP**：接続の成否、接続時間、状態の変化、失敗の継続
- **HTTP**：応答コード、応答時間、設定した期待値との一致
- **認証**：一定時間内に集中したログイン失敗
- **収集状態**：認証ログが直近まで正常に取得されているか

「異常の有無」だけでなく、**何を観測し、どの条件で異常と判定したか**を確認できることを重視しています。

## 主な機能

| 機能 | 判定・記録内容 |
| --- | --- |
| TCP接続監視 | 指定したポートへの接続成否と接続時間 |
| TCP異常検知 | 状態変化、応答遅延、連続接続失敗 |
| TCPの期待状態判定 | ポートが `OPEN` / `CLOSED` のどちらであるべきかを設定して比較 |
| HTTP監視 | 指定したパスへのGET要求、応答コードと応答時間 |
| HTTP異常検知 | 期待する応答コードとの不一致、応答遅延、異常の継続・回復 |
| 認証失敗集中の検知 | 60秒間に5回以上の失敗が発生した送信元IP・ユーザー名を検出 |
| 収集状態の確認 | 最終取得成功時刻を用いて `stale`（情報が古い状態）を判定 |
| 記録・表示 | CSV、JSON API、ブラウザ用ダッシュボード |

TCPの「異常検知」と「期待状態判定」は別の評価です。例えば、閉じていることが正常なポートでは、`CLOSED` を期待値として設定できます。

認証失敗の集中は**調査が必要な兆候**であり、それだけで不正アクセスや攻撃と断定するものではありません。

## システム構成

```text
                  監視対象サービス
                   ├─ TCP接続
                   └─ HTTP GET
                         │
                         ▼
                   C言語監視ツール
                   ├─ TCP・HTTP判定
                   ├─ CSV記録
                   └─ Web API / ダッシュボード

  模擬金融APIの認証イベント（開発環境）
                   │
                   ▼
              JSONL形式のログ
                   │
                   ▼
         外部のログ収集・変換処理
           （本リポジトリには未同梱）
                   │
                   ▼
               正規化TSV
                   │
                   ▼
             C言語の認証検知
                   └─ /api/auth-status
```

開発時にはWindows、WSL Debian、Ubuntu Serverの仮想マシンを使用し、UbuntuのFastAPIへSSHトンネル経由で接続しました。認証ログの取得には、別途WindowsタスクスケジューラとSSH鍵認証を使用しています。

**このリポジトリだけで利用できる範囲**は、C言語によるTCP・HTTP監視と、外部で用意した正規化認証TSVの判定・表示です。模擬金融APIの構築や認証ログの自動取得までは含みません。

## 動作環境

- Linux
- GCC
- GNU Make
- POSIXスレッド（pthread）を利用できる環境

開発・検証にはWSL Debianを使用しました。その他のLinux環境での動作は、個別に検証が必要です。

## ビルドと起動

プロジェクトのルートディレクトリで実行します。

```bash
cp data/config.example.txt data/config.txt
make
./monitor
```

サンプル設定では `127.0.0.1:18000` の `/health` を監視し、Web画面に8082番ポートを使用します。**起動前に監視対象となるHTTPサービスを別途用意してください。** サービスがなければ接続失敗が記録されます。

監視対象の応答確認例：

```bash
curl -i http://127.0.0.1:18000/health
```

画面とAPIの確認先（サンプル設定の場合）：

- ダッシュボード：`http://127.0.0.1:8082/`
- TCP・HTTPの状態：`http://127.0.0.1:8082/api/status`
- 認証の状態：`http://127.0.0.1:8082/api/auth-status`

上記の `127.0.0.1` は**接続元からのアクセス先**を示します。C言語のWebサーバはIPv4ループバックアドレス（127.0.0.1）で待ち受けます。ただし、Windows側のポート転送などによる到達範囲は別途確認が必要です。検証用Webサーバをインターネットへ公開しないでください。

## 設定ファイル

`data/config.txt` は `key=value` 形式です。

| 項目 | 説明 |
| --- | --- |
| `ip` | 監視対象のIPv4アドレス |
| `start_port` / `end_port` | TCP監視対象のポート範囲 |
| `interval` | 監視間隔（秒） |
| `web_port` | ダッシュボードの待受ポート |
| `expected_state` | 基本の期待状態（`OPEN` / `CLOSED` / `OBSERVE_ONLY`） |
| `http_port` | HTTP監視対象のポート。`0` ならHTTP監視を無効化 |
| `http_path` | HTTP GETの対象パス |
| `http_expected_status` | 正常とみなすHTTPステータスコード |

HTTP監視対象のポートは、TCP監視のポート範囲にも含めてください。ポートごとの期待状態など、詳細はソースと `docs/ARCHITECTURE.md` を参照してください。

## 認証ログの監視

C言語監視ツールは、生の認証JSONLではなく、外部の収集・変換処理が生成したTSVを読み込みます。

TSVは1行につき次の4列です（タブ区切り）。

```text
epoch_ms<TAB>failure_flag<TAB>source_ip<TAB>username
```

- `epoch_ms`：イベント発生時刻（Unix時刻、ミリ秒）
- `failure_flag`：ログイン成功は `0`、失敗は `1`
- `source_ip`：記録された送信元IPアドレス
- `username`：ログインに使用されたユーザー名

もう1つの入力である `poll-heartbeat.txt` には、取得済みイベント件数を記録します。その**ファイル更新時刻**を最後の収集成功時刻として扱います。これは認証イベントの発生時刻とは別です。ログインが発生しない時間帯でも、収集処理が稼働しているかを確認するために分離しています。

入力ファイルの場所は環境変数で指定できます。

```bash
export NM_AUTH_TSV="/path/to/private/auth-normalized.tsv"
export NM_AUTH_HEARTBEAT="/path/to/private/poll-heartbeat.txt"
./monitor
```

未指定の場合は `data/auth-normalized.tsv` と `data/poll-heartbeat.txt` を参照します。これらの実データはGit管理に含めないでください。

`/api/auth-status` では、検証済みの主な状態として次を扱います。

| 状態 | 意味 |
| --- | --- |
| `alert` | 現在有効な認証失敗集中の警告がある |
| `no_alert` | 収集データが新しく、現在有効な警告はない |
| `stale` | 収集データの更新が止まっている、または古い |

Web APIには送信元IP・ユーザー名の個別値を表示しない設計です。ただし、**入力TSV自体には識別情報が含まれます**。ファイルの保存先と権限には注意してください。

## 検証結果

2026年10月25日、公開候補を別ディレクトリへコピーしてビルドし、**142件の回帰チェックすべてに合格**しました。

| 検証範囲 | 合格数 |
| --- | ---: |
| TCP・HTTP関連 | 113 |
| 認証検知・状態管理・CSV | 29 |
| **合計** | **142** |

回帰チェックには単体テスト、モジュール単位の検証、HTTP通信を伴うテストが含まれます。すべてを「単体テスト」と呼んでいるわけではありません。

公開候補のWeb APIについても、環境変数で指定した認証TSVからの `alert`、時間窓経過後の `no_alert`、収集停止時の `stale`、認証APIでのIPアドレス・ユーザー名の非表示、従来の `/api/status` との互換性を確認しました。

開発環境では、模擬金融APIのログイン失敗から認証イベントの収集、警告CSVの生成までを確認しています。また、定期収集の追加イベント取得と重複防止、ブラウザでのTCP・HTTP監視結果の表示も確認しました。これらの自動収集環境は本リポジトリに含まれません。

詳しくは [検証記録](docs/TEST_EVIDENCE.md) を参照してください。

## 技術選定と設計上の判断

**C言語を採用した理由**は、ソケット通信、タイムアウト、スレッド、共有データの排他制御を自分で実装し、動作を理解するためです。ポートごとの監視をpthreadで並列化し、共有する監視結果をmutexで保護しています。

**HTTP監視を加えた理由**は、TCP接続が成功しても、APIが期待したHTTP応答を返すとは限らないためです。接続の成否とアプリケーションの応答を別の項目として確認します。

**ログ収集の時刻を分けた理由**は、最後の認証イベントが古いことと、収集処理が停止していることは同じではないためです。収集成功時刻を別に管理し、データが更新されていない状態を無警告と混同しないようにしています。

詳細は [システム構成・技術選定](docs/ARCHITECTURE.md) に記載しています。

## 制約

- 認証失敗集中の検知だけで、不正アクセスと操作ミスを区別することはできません。
- TCP接続の成功やHTTPステータスの一致だけでは、業務処理全体の正常性は保証できません。
- このリポジトリには模擬金融APIと認証ログ自動収集器が含まれず、それらの構築手順を含む完全な再現環境ではありません。
- 長期間・高負荷での運用試験や、攻撃検知の精度評価は実施していません。
- Webサーバ自体はIPv4ループバックアドレスにバインドしますが、OSのネットワーク設定による公開範囲には注意が必要です。外部公開を前提とする認証・暗号化などの機能は備えていません。

本ツールは、通信監視と異常判定の仕組みを学び、ローカル環境で検証するためのものです。
